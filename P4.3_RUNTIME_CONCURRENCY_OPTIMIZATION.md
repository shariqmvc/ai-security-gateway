# B.5-P4.3 Runtime / Concurrency Optimization

## Implemented change

Added an opt-in, provider-wide fair semaphore for downstream provider execution.
The first target is Ollama because B.5-P4 benchmarking established that the
shared `llama3.1:8b` runtime is the dominant latency/failure bottleneck under
synchronized multi-tenant concurrency.

### Configuration

```yaml
gateway:
  provider:
    concurrency:
      providers:
        OLLAMA:
          max-concurrent: ${GATEWAY_OLLAMA_MAX_CONCURRENT:0}
          acquire-timeout: ${GATEWAY_OLLAMA_CONCURRENCY_ACQUIRE_TIMEOUT:0s}
```

`max-concurrent: 0` disables the guard and preserves prior behavior.

### Intended P4.3 experiment

```text
GATEWAY_OLLAMA_MAX_CONCURRENT=2
GATEWAY_OLLAMA_CONCURRENCY_ACQUIRE_TIMEOUT=75s
GATEWAY_OLLAMA_READ_TIMEOUT=60s
GATEWAY_ROUTING_FAILOVER_ENABLED=false
```

Run the existing synchronized C5 workload: 3 Tenant-A requests + 2 Tenant-B
requests per round, 10 rounds, 50 total requests, same prompt/model.

## Design rationale

- The limiter is provider-wide so it protects the shared downstream Ollama
  runtime rather than creating an artificial tenant-specific capacity split.
- Semaphore fairness is enabled to reduce starvation risk among concurrent
  tenant requests.
- Permit release is guaranteed with try-with-resources.
- The acquire wait is capped by the active request budget when one exists.
- The limiter is disabled by default so this change is not silently altering
  existing production behavior.

## Validation status

Unit tests were added for disabled mode, immediate rejection, and delayed

## Benchmark decision gate

Compare C5/60s without the guard against C5/60s with `max-concurrent=2`.
Success rate, P50/P95, timeout count, tenant fairness, and provider latency
must all be evaluated before adopting a non-zero default.
